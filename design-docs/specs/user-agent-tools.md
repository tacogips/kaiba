# Personal AI Agent with In-Process Kaiba Tools

## Status

Accepted

## Traceability

- Predecessor: `design-docs/specs/ai-agent-integration.md` (AI1-AI11). This
  document adds a second agent runtime behind the same `AgentInvoking` /
  `AgentStreamingInvoking` seams; it does not change the gateway adapter.
- Ownership rules consumed unchanged: `design-docs/specs/multi-user.md`,
  `design-docs/specs/library.md`.
- Implementation plan: `impl-plans/completed/user-agent-tools.md`.

## Problem

Kaiba's existing AI features run every request through one server-configured
`agent-gateway` vendor and one server-held credential. The model receives a
flattened prompt and returns text; it cannot call any kaiba operation. Two
requests are therefore unmet:

1. A user wants the agent to run on **their own API key**, not the operator's.
2. A user wants the agent to **do arbitrary work in kaiba** (search, read,
   create, edit, tag, link, undo) rather than only answer about one note.

## Summary

Kaiba gains a **personal agent runtime**:

- Each user may store one provider credential (API key, provider, default
  model) in the note store. The key is written through GraphQL or the CLI and
  is never readable back; only a 4-character hint is exposed.
- When a user who has an enabled credential sends a chat turn, the reply is
  generated by an **in-process tool loop**: kaiba calls the provider's HTTP
  API directly with the user's key, streams text to the existing reply
  stream, executes every requested tool **inside the server process**, and
  repeats until the model ends its turn.
- The tools are typed wrappers over `NoteService`, bound to a service value
  **scoped to the acting user** (`scoped(to:)`), so the agent can do exactly
  what that user could do through the GraphQL API and nothing more.
- Users without a credential (or with it disabled) keep the existing
  server-configured gateway path unchanged.

## Design Decisions

### UA1. One credential per user, stored in the note store

Table `user_agent_credentials` (`Sources/AppCore/NoteStoreSchema.swift`):

| column | meaning |
| --- | --- |
| `user_id` (PK, FK users) | the owner; exactly one row per user |
| `provider` | `anthropic`, `openai`, `openrouter`, or `openai-compatible` |
| `api_key` | the secret, stored as given |
| `base_url` | optional endpoint override (see UA2) |
| `default_model` | the model id used for every personal-agent turn |
| `enabled` | 0/1; a disabled row falls back to the server runtime |
| `created_at`, `updated_at` | timestamps |

Storage is plaintext inside the sqlite store, alongside `auth.jwt.secret`
which the store already holds in `app_settings`. An encryption key resident in
the same database would add no protection against database theft, and kaiba
has no operator-side key material outside the store. The protection offered
is **API-surface protection**: no query, DTO, CLI output, log line, or error
message ever includes `api_key`. `UserAgentCredentialSummary` (the only shape
that leaves `AppCore`) carries `keyHint` = the last four characters.

Access rules (`NoteService+UserAgentCredentials.swift`):

- A **scoped** principal (`actingUserId != nil`, not unauthenticated) reads,
  writes, and clears only its own row.
- An **unauthenticated** principal (`--allow-unauthenticated` requests) is
  refused with `notFound`, so a public host never accepts or reveals a key.
- The **unscoped operator** (local CLI, no `--jwt`) must name the target with
  `--user <id>`; an enabled administrator acting through a scoped service may
  also target another user. Anyone else naming another user gets `notFound`.

Validation: `apiKey` is 1-4096 printable characters without whitespace;
`defaultModel` is 1-200 characters; `baseURL` must parse as an `http(s)` URL
with a host and no credentials or query.

### UA2. Providers and endpoints

The runtime speaks two wire formats directly over HTTPS; no subprocess and no
vendor CLI is involved:

| provider | wire format | default base URL |
| --- | --- | --- |
| `anthropic` | Anthropic Messages API (`POST /v1/messages`, SSE) | `https://api.anthropic.com` |
| `openai` | OpenAI Chat Completions (`POST /chat/completions`, SSE) | `https://api.openai.com/v1` |
| `openrouter` | OpenAI Chat Completions | `https://openrouter.ai/api/v1` |
| `openai-compatible` | OpenAI Chat Completions | none; `baseURL` required |

A user-supplied `baseURL` makes the server open outbound connections to a
host of the user's choosing. It is therefore accepted only when the operator
sets `ai.userAgent.allowCustomBaseURL: true`; otherwise `baseURL` must be
absent and `openai-compatible` is rejected. Anthropic requests send the key
as `x-api-key` with `anthropic-version: 2023-06-01` (a custom base that
already ends in `/v1` is not doubled); OpenAI-compatible requests send
`Authorization: Bearer`. Anthropic requests place a prompt-cache breakpoint
on the system prompt (caching the tool declarations and instructions) and on
the last message, so each tool round reuses the previous round's prefix.
Anthropic requests ask for 16,000 output tokens per round; when a model's
cap is lower the provider rejects the request with HTTP 400 naming
`max_tokens` and quoting the cap, and the request is retried once with that
cap (4,096 when none is quoted). There is no per-model table and no setting.

### UA3. Tool loop

`UserAgentToolLoopRunner` implements `AgentStreamingInvoking` and
`AgentInvoking`:

1. Build the system prompt from the request's system prompt, the subject
   context (`contextMarkdown`, as a `<document>` block), and the tool
   guidance. Prior turns become alternating user/assistant messages; the
   current user turn is the last message (a blank user turn is sent as
   `(empty message)`, since providers reject empty text). Note-edit turns
   (`AgentInvocationRequest.allowsTools == false`) are sent without tools or
   tool guidance: their reply is the replacement body the server applies
   itself, so the model must not also rewrite the note behind it.
2. Call the provider with the tool definitions. Text deltas are coalesced
   into chunks for `onChunk`: a chunk is released when it reaches 1 KiB
   (256 KiB / 256, so the relay's chunk budget cannot be exhausted before its
   byte budget), or, while fewer than 64 chunks have been sent, when the
   buffered text is older than 500 ms at the next delta so short replies
   still stream promptly. Whatever a round produced is always flushed before
   the next provider request. The existing `AgentReplyChunkRelay` applies the
   256 KiB / 256-chunk budget; a `false` return aborts the loop.
3. If the turn ends with tool calls, execute every call through
   `AgentToolExecuting` in order, append one visible activity line per call
   (`> tool \`name\` -- ok` or `-- error: ...`), send the results back as a
   single tool-result message, and repeat.
4. Stop on `end_turn`, on `max_tokens` (the partial text is kept and a
   marker is appended), on `refusal` (a fixed explanation is the reply), or
   when the round budget `ai.userAgent.maxToolRounds` (default 24) is spent
   (a marker is appended and the loop ends).

The persisted reply is exactly the concatenation of what was streamed, so a
client that watched the stream and a client that loads the answered turn see
the same markdown.

Tool results are JSON documents bounded to 48 KiB each (a truncation marker
replaces the tail); a note body inside a result is bounded to 32 KiB first,
so a `get_note` payload for a large note stays complete JSON. Tool call
inputs are parsed as JSON, never string-matched.
A tool that throws produces an `is_error` result and the loop continues; the
model decides how to recover.

### UA4. The toolbox is the kaiba API, scoped to the user

`KaibaAgentToolbox` wraps a `NoteService` that the dispatcher has already
scoped to the originating principal and fenced to the outbox lease. Every
ownership, library, read-only, and account check that protects GraphQL
therefore protects the agent without duplication. Tools:

| tool | service call |
| --- | --- |
| `search_notes` | `searchNotes(query:notebookId:limit:)` |
| `get_note` | `getNote` + `listComments` + `listLinks` |
| `list_notebooks` | `listNotebooks(limit:offset:)` |
| `get_notebook` | `getNotebook` + `listNotes(notebookId:limit:offset:)` |
| `create_notebook` | `createNotebook(title:)` |
| `create_note` | `createNote(notebookId:notebookTitle:title:bodyMarkdown:tags:provenance: .ai)` |
| `update_note_body` | `updateNoteBody(noteId:bodyMarkdown:provenance: .ai)` |
| `add_comment` | `addComment(noteId:bodyMarkdown:author: "agent")` |
| `apply_note_tags` | `applyTags(noteId:tags:provenance: .ai)` |
| `remove_note_tag` | `removeTag(noteId:tagName:removedBy: .ai)` |
| `list_tags` | `listTags()` |
| `link_notes` | `linkNotes(from:to:linkKind:provenance: .ai)` |
| `delete_note` | `deleteNote(noteId:)` |
| `undo_last_action` | `undoLastAction()` |

Deliberately absent: files and attachments (server file system access),
libraries and members, users, API clients, auth, import, storage migration,
auto-action configuration, and store maintenance. The agent also may not
write into an `agent-conversation` notebook (its own transcript) through
`create_note`, `update_note_body`, `add_comment`, `apply_note_tags`,
`remove_note_tag`, `link_notes` (either endpoint), or `delete_note`; those
calls return an error result.
Every write carries provenance `ai` and is recorded in the action log, so
`undo` covers agent work exactly as it covers a human's.

### UA5. Routing

`KaibaAutoActionDispatcher.dispatchChatReply` chooses the runtime per turn:

1. If the dispatch principal is an authenticated user with an **enabled**
   credential and `ai.userAgent.enabled` is true, the personal runtime is
   built for that turn with the user's key and a toolbox over the dispatch
   service. The model is always `default_model`; a model snapshot recorded
   on the turn is ignored for this runtime.
2. Otherwise the server-configured gateway invoker is used as before.
3. If neither exists the turn fails with a clear message and the outbox retry
   budget applies.

The dispatcher is now created whenever either runtime can exist, so a server
with no `ai.agent` section still answers personal-agent chats. Because the
dispatcher may exist without any runtime for a given user,
`sendAgentChatMessage` asks the dispatcher (`canAnswerChat(for:)`) before
queueing: a user with neither a gateway nor an enabled credential gets an
`agent-unavailable` turn immediately, exactly as before this feature. Tag
extraction, translation, and agentic search are unchanged and continue to
require the server runtime.

`agentModels` reports the acting user's `default_model` as the configured
model (status `ok`, no discovery) when that user has an enabled credential and
the feature is enabled, so the composer's model selector and turn validation
work without a server catalog.

### UA6. Configuration

```json
{
  "ai": {
    "userAgent": {
      "enabled": true,
      "allowCustomBaseURL": false,
      "maxToolRounds": 24
    }
  }
}
```

All fields are optional; the defaults above apply when the section or the
whole `ai` section is absent. `enabled: false` hides the credential surface
(queries answer `feature-disabled`, mutations are rejected) and routes every
chat to the server runtime.

### UA7. Surfaces

- GraphQL: `userAgentCredential` query; `setUserAgentCredential`,
  `setUserAgentCredentialEnabled`, `clearUserAgentCredential` mutations. The
  payload is `{ result, featureEnabled, providers, credential? }` where
  `credential` is the summary (never the key).
- CLI: `kaiba ai credential set|show|clear|enable|disable` with `--user <id>`
  for the operator. The key is read from an environment variable
  (`--api-key-env NAME`) or stdin (`--api-key-stdin`), never from an argument,
  so it does not land in shell history or process listings.
- Web: a "Personal AI agent" card on the Config screen (provider, API key,
  model, optional base URL, enable toggle, save/clear), showing the stored
  hint and model. The chat composer needs no change.

### UA8. Admission and limits

Personal-agent turns pass the same `admitAutoActionProviderInvocation` gate
and per-principal admission slots as gateway turns. Provider HTTP requests
time out after 10 minutes of silence; each tool round is one HTTP request.
The reply budget is the existing 256 KiB / 256 chunks.

## Rejected Alternatives

- **Extending agent-gateway with a tool channel.** ACP has no host-tool
  protocol for API vendors, the gateway is a separate release train, and a
  subprocess per turn would still need an IPC channel back into the server
  for each tool call.
- **Exposing kaiba as an MCP server for CLI vendors.** Only the coding-CLI
  vendors could consume it, and those are exactly the vendors refused for
  served requests because they execute arbitrary tools.
- **A generic `run_kaiba_command(argv)` tool.** It would expose the whole CLI
  including file-system and store-control verbs; an allowlist plus argv
  scrubbing is more fragile than typed tools over the service.
- **Per-provider multiple credentials per user.** Adds a selector to every
  surface for no present need; one active credential is enough.
